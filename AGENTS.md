# Working on route-gpx

This file is the single source of agent instructions. `CLAUDE.md` only imports it for Claude Code and adds tool-specific notes; keep project instructions here.

## Purpose and scope

route-gpx is a static route planner with GPX import/export, built with HTML, strict TypeScript, Vite and Leaflet. It runs in the browser. It is published on GitHub Pages at the custom domain `https://route-gpx.t00ls.dev/` with a `/` base; the old project URL `https://t00ls-dev.github.io/route-gpx/` redirects there. There is no application backend, account system, analytics or remote AI. Keep changes compatible with this architecture unless the task explicitly changes it.

Present the project as a route planner with GPX export. Keep public introductions, SEO and sharing assets neutral about transport mode and languages. Language support belongs in the interface selector and the README feature list; do not promote it as a project tagline. Preserve accurate technical explanations of the routing services and their current driving profile where they explain behavior or configuration.

Route creation uses addresses, coordinates and map points. The route-description interpreter has been removed; keep this direct editing flow simple.

## Contracts to preserve

- `Coord` is `[latitude, longitude]`. OSRM URLs and GeoJSON use longitude first; convert at the adapter boundary. Preserve every full-resolution track point and separate GPX track segments. Escape user-provided XML text.
- Server URLs live in two places by design: OSRM, Valhalla and Nominatim are part of `State` (links when non-default, JSON editor, saved routes, backups); Photon, Open-Meteo and the IP-region service are device preferences in localStorage (`photon-url`, `weather-server`, `region-url`) and never enter links, saved routes or backups; the same applies to the `average-speed`, `distance-units`, `temperature-units`, `route-coloring`, `route-arrows`, `weather-markers` and `auto-departure` preferences. Moving a server between the two changes the state/link format and needs compatibility handling.
- Servers carried by a link are never used without an explicit choice: a link with non-default routing/search servers opens with the defaults and a notice offers Use link servers. Settings, the JSON editor, saved routes and backups remain explicit user flows.
- Router responses are untrusted: the OSRM and Valhalla adapters build routes through `validRoute` (also used for backups) and reject malformed geometry or values, letting OSRM failures fall back to Valhalla.
- Route steps may carry optional maneuver details: `kind` in OSRM's maneuver-type vocabulary, `modifier` from `MODIFIERS`, a roundabout `exit` (integer 1–20) and the maneuver location `at` as `[lat, lon]`. Both adapters map to this shared vocabulary (Valhalla through `VALHALLA_TYPES`) and omit values outside it; `validRoute` rejects malformed ones in saved routes and backups. The fields stay optional so older saved routes and `route-gpx-library` v1 backups remain valid and reopen without rerouting.
- Imported GPX, TCX and FIT geometry remains exact until a point edit causes rerouting. FIT and TCX import reads only geometry, names, course points and recorded elevation, locally; sensor data is ignored and never stored, and export stays GPX only. A share link stores controls/options, not that geometry, and recalculates when opened. Do not imply that links preserve imported tracks.
- `State` uses version 1. Links are written as `#v2=` (base64url raw DEFLATE via fflate of a positional array, coordinates rounded to 6 decimals, default servers omitted) and `#v1=` links (base64url JSON) remain readable. Keep existing links and the advanced JSON editor compatible; validate links, editor JSON and backups with `validateState` rather than trusting parsed JSON. Legacy speed and `units` values in links, editor JSON and backups are ignored without discarding valid route points.
- Editing a route invalidates the current result and disables stale downloads. Preserve revision checks and discard superseded work so late routing/search responses cannot overwrite newer input or another point's results.
- Language, units and GPX coordinates are independent. Units are device preferences chosen in Settings (`src/unit-preferences.ts`): distance (km/mi: distances, speeds, wind, altitude) and temperature (°C/°F, with weather precipitation in mm/in), each Automatic by default, inferred locally from the browser's language region and then its time zone, never from a request. Links, saved routes and backups do not carry units (the `#v2=` units slot is kept as 0). Weather requests and risk thresholds stay metric; unit changes only reformat and must not reroute, refetch or alter geometry. Time, arrival, weather passage times and daylight all use the traveler's average speed, never the router duration. That speed is a device preference in localStorage (`average-speed`, default 60 km/h) changed only by the user (slider, or the unit switch converting it); links, saved routes and backups do not carry it, and legacy values in them are ignored (the `#v2=` speed slot is kept as 0).
- Undo retains up to 50 snapshots in memory, each holding a reference to the route shown for it, so undo restores that exact geometry without rerouting; there is no separate route cache for undo. Preserve point move/removal/reordering behavior and the keyboard shortcut's exclusion of text inputs.
- Routes are saved only by an explicit named save. IndexedDB entries use normalized names for updates; reopening/downloading stored geometry must not request a new route. The one request allowed for a stored route is the step-only refresh when the Itinerary of a route saved before maneuver details existed is opened (`src/directions.ts`): its steps replace the old ones only when the fresh route follows the saved geometry (`sameRoad`), and `updateSavedSteps` stores only the steps, keeping geometry, name and dates; when the road changed, `markDirectionsChecked` records it in the entry (optional `directionsChecked`) so it is not asked again. Storage failure must leave ordinary GPX download usable.
- Backups use the `route-gpx-library` version 1 format. Validate the complete import before writing and keep existing entries with matching names. Do not silently discard saved data or change persistence formats without handling compatibility.
- “Prefer main roads” is a heuristic review aid, not a guarantee. Keep provider road references factual; do not invent classifications.

## Network behavior and privacy

Use the adapters in `src/services.ts` for routing/search. Imported tracks get turn directions only when the Itinerary is opened, through OSRM map matching (`osrmMatch`): points evenly spaced within each leg (restarting at every route point, spacing ladder from 300 m, about 40 requests), requests of at most 10 points (the public server's limit) that never cross a route point, on the routing queue, without retries, with a page-memory cache of 400 requests for 15 minutes so an edit re-requests only the changed legs; the imported geometry never changes. OSRM is primary, with a delayed Valhalla fallback. Preserve serialized routing starts at least 1.5 seconds apart, the 900 ms route-change debounce, and suppression of stale queued calculations. Do not introduce retry loops. The one exception is the Open-Meteo usage limit (the shared per-page budget of 599 coordinates a minute, 4,999 an hour, 9,999 a day and 299,999 in 31 days, or HTTP 429): weather and elevation show a live countdown (`countdown`, "Try again in 30s.") with no retry button, then retry once on their own; refused again, they count down once more and only then show the button. Use Retry-After when the response exposes it, otherwise wait 60 s.

Nominatim searches are explicitly triggered with Enter, not autocomplete. Photon suggests places while typing; do not restore the removed search buttons. Preserve the 500 ms UI debounce, 1.1-second search spacing, in-memory query cache and cross-tab coordination through Web Locks/timestamp storage where available. The timestamp is not a location store. Client-side limits do not enforce aggregate traffic limits across devices.

Keep fetch credentials omitted and service URL validation intact. Retain visible OpenStreetMap attribution. Do not add tile prefetching, bulk downloads or offline tile caching. Locations belong only in the existing explicit route/link/storage flows; canonical URLs, social metadata and sitemap entries must never contain user route state.

Weather is optional: no departure means no Open-Meteo request. A valid departure triggers a debounced request automatically. Without a chosen departure, the automatic departure (`src/departure.ts`) is the next local :00/:30 slot (`nextDepartureSlot`): it applies once the route is ready (so weather is requested without a click), moves forward at each slot while the page is visible (not while the field has focus, catching up when a hidden tab returns) and is used by weather, daylight, arrival and playback through `departureOf`. It lives in page memory only and never enters links, saved routes, backups or the JSON editor; only a departure the user chose is `state.departure`. The Automatic departure checkbox below the field shows the mode: any user edit fixes the departure and unchecks it, clearing turns it off until reload, checking it returns to automatic, and unchecking it by hand stores the `auto-departure` device preference as off. Without a departure, Weather asks for one. Support the last 90 UTC calendar days and the 16-day forecast horizon. Sample about every 20 km (or one hour for slow travel), including controls, with at most 20 points; consecutive samples with equivalent conditions (`groupWeather`, `MERGE_THRESHOLDS` in `src/weather-risk.ts`) share one card and one marker with ranges, while start, stops and destination always keep their own; with more than 20 controls, keep start and destination and choose the controls closest to an even spread (named before automatic stops) and say how many were sampled, never fail or ask the user to remove points. Use a worst-case ±1 hour window rounded outward. Keep weather and sampling coordinates in page memory only; only departure belongs in existing explicit route/link/backup flows. Wind direction is meteorological (from), compared with the local full-resolution track bearing; use the outgoing edge at bends and incoming edge at the destination, never GPX segment gaps. Show head/tail/crosswind at the nearest hour in selected units; do not imply apparent wind or vehicle resistance. Do not restore the removed planned-stop field or forecast button. Slower speeds may require additional points; otherwise recalculate times locally.

Keep route caching bounded to 20 results for 15 minutes; Calculate route bypasses it. Weather caches are per rounded location and interval, at most 200 locations/100,000 hourly entries for ten minutes. Cache hits must not extend freshness. All these caches stay in page memory. Map wind arrows show the direction wind blows toward; colors indicate head/tail/crosswind relative to the route; calm or unknown is neutral. Mean-wind strength remains separate from gust risk thresholds.

Elevation is requested only when the user opens Elevation (a recalculated route waits 2 s to settle while the row is open): at most about 300 sampled route points, evenly spaced within each leg from a fixed spacing ladder so an edit re-requests only the changed legs, to the configured Open-Meteo server (`/v1/elevation`), in serialized chunks of 100, no retries, page-memory cache of 5,000 locations for ten minutes; recorded elevation from imported GPX `<ele>`, TCX `AltitudeMeters` or FIT altitude is used locally without requests and is not stored. Daylight is calculated locally from the route and the same passage times as weather (the device average speed, no stops): no requests and no stored data. Route coloring and route marks are visual only and never change the route, links or GPX. Weather belongs to the route: it is shown only for the departure-based samples along it. Do not add map-wide weather overlays such as rain radar, cloud or forecast layers (rain radar was removed). Keep weather attribution in the existing map credits dialog. No service worker or installation flow.

## Local validation

Use Node.js 22 LTS 22.23.4 or newer, Node 24.15 or newer in the 24 line, or Node 26+ (CI uses Node 22.23.4), and `npm ci` for a reproducible install. The 24.15 minimum comes from jsdom 31 (unit-test environment), which requires Node `^22.22.2 || ^24.15.0 || >=26.0.0`; keep the `engines` field in `package.json` within the ranges required by the development dependencies, and update the README when it changes. Keep `@types/node` on the 22 line so type checks match the minimum supported runtime (Dependabot ignores its major updates). `npm run dev` serves the application at `http://localhost:5173/` by default; the help page is a second Vite entry.

For application changes, run the CI checks:

```sh
npm run lint
npm run format:check
npm test
npm run test:browser
npm run build
```

Install Chromium with `npx playwright install chromium` if needed. Playwright starts its own dev server on `127.0.0.1:5173`; avoid an unrelated server occupying that port. For documentation-only edits, run `npm run format:check` and check the documented commands/paths against the repository; no application test is needed solely for prose.

- Regular tests must mock all external HTTP services, including tiles and IP lookup. Date-sensitive tests must fix the clock. Keep tests independent of execution order, shared files and persistent state across workers or shards; the opt-in live integration/acceptance commands are the explicit exceptions.
- Vitest runs `tests/**/*.test.ts` in jsdom. Cover core/GPX, state, service adapters, history, units/time, translations and backup validation in their corresponding files when changing those contracts.
- Playwright runs `tests/*.spec.ts` in Chromium, fully parallel (tests are distributed individually, not by file) with one worker. `points.spec.ts` covers desktop/mobile workflows and storage/download regressions; `panel.spec.ts` covers the side panel, bottom sheet heights, More actions and the Settings dialog; `metadata.spec.ts` covers localized SEO and Pages assets. Extend relevant scenarios for behavioral regressions and mock public services as existing tests do.
- `npm run test:integration` is opt-in and calls real public OSRM. Its default skip is expected; report whether it actually ran.
- `node scripts/browser-check.mjs` is a separate acceptance script requiring a local server, or `SITE_URL` for a deployed site. It calls real routing, reads `docs/example.gpx` as a fixture and writes captures, downloaded GPX and its report only to the ignored `.browser-check.local/` folder. Never overwrite the tracked fixture or add generated screenshots/reports to the repository. Run it only when those live checks are relevant and avoid repeated public-service traffic.

The complete browser suite runs with `npm run test:browser`; a local shard runs with `npm run test:browser -- --shard=1/4` (through `4/4`). CI splits the suite into 4 shards, each with one Chromium worker and a development server; with `CI` set, shards write blob reports that the `merge-reports` job combines into an HTML `playwright-report` artifact. Production-preview testing remains pending; do not describe it as implemented.

## Git and GitHub operations

Use the local `git` and `gh` executables for Git and GitHub operations. Do not replace them with GitHub APIs or connectors integrated into the harness. Calls through the local `gh api` command are permitted.

Use the existing authentication; do not create parallel credentials. Do not add authorship credits to Codex, Claude Code, OpenAI or Anthropic in commits, pull requests, code or documentation, including `Co-authored-by` trailers. Preserve existing licenses, mandatory legal attribution and repository history.

`main` is protected by the `Protect main` repository ruleset: pull requests are required, merges are squash-only with linear history, the `Lint, test and build` CI check must pass on a branch that is up to date with `main`, and review conversations must be resolved. Force-pushes and deletion are blocked, and the ruleset has no bypass actors. Never push directly to `main` or try to work around these protections. Releases follow the manual process in `CONTRIBUTING.md`; never create tags or GitHub Releases without explicit authorization.

Changes reach `main` only through pull requests. Create a focused branch named `<type>/<short-description>` (for example `fix/gpx-import-names`), push it, open the PR with `gh pr create` following `.github/pull_request_template.md`, watch its CI run and merge with `gh pr merge --squash --delete-branch` only when the merge is authorized. The PR title becomes the squash commit title, so write it in the history's concise imperative English style.

The required check is the CI gate job `Lint, test and build`, which depends on the static-check job and every browser shard. Renaming that job breaks the required check; such a change must update the ruleset in the same authorized task. Changing, disabling or bypassing rulesets, merge settings or security features (Dependabot alerts and security updates, private vulnerability reporting) is a separate repository-administration task that needs its own authorization.

## Hosting and publication

Pages serves the custom-domain root with an approved certificate and enforced HTTPS. Changing the Pages domain, DNS or HTTPS settings is a separate authorized infrastructure task. Preserve Vite's `/` base for the custom domain and the app, help and What's new (`changelog.html`) build entries. A hosting-path change also requires reviewing manifest `id`/`start_url`/`scope`, canonical/social URLs, sitemap and docs; root-relative paths can break on a Pages project site.

Two workflows handle checks and publication. `.github/workflows/ci.yml` (CI) runs the static checks, unit tests and build in one job and the browser suite in 4 shards, merges their reports and reports the result through the `Lint, test and build` gate job for pull requests, main pushes and manual dispatch with only `contents: read`, in the non-cancelling `ci-<ref>` concurrency group. `.github/workflows/deploy.yml` (Deploy) runs through `workflow_run` only after a CI run triggered by a push to `main` succeeds; it rebuilds that run's exact `head_sha` and publishes it to Pages. Preserve Deploy's `pages: write` and `id-token: write`, its non-cancelling `pages` concurrency group and its current-main guard, which skips publication when the commit is no longer the current `main` so an older commit cannot publish over a newer one. Keep Pages permissions out of CI and do not add a manual trigger to Deploy. Never rerun old workflow executions to publish; watch only the runs belonging to the authorized new commit.

When publication is part of the task, deliver the change through an authorized pull request as described above; the push to `main` comes from its squash merge. Then follow the CI run for the merge commit on `main` and the Deploy run it triggers with `gh run watch <id> --exit-status`, and distinguish successful checks from successful deployment. Confirm the requested behavior on the live site; do not infer it from a green build alone.
