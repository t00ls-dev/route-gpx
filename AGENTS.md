# Working on route-gpx

This file is the single source of agent instructions. `CLAUDE.md` only imports it for Claude Code and adds tool-specific notes; keep project instructions here.

## Purpose and scope

route-gpx is a static route planner with GPX import/export, built with HTML, strict TypeScript, Vite and Leaflet. It runs in the browser. It is published on GitHub Pages at the custom domain `https://route-gpx.t00ls.dev/` with a `/` base; the old project URL `https://t00ls-dev.github.io/route-gpx/` redirects there. There is no application backend, account system, analytics or remote AI. Keep changes compatible with this architecture unless the task explicitly changes it.

Present the project as a route planner with GPX export. Keep public introductions, SEO and sharing assets neutral about transport mode and languages. Language support belongs in the interface selector and the README feature list; do not promote it as a project tagline. Preserve accurate technical explanations of the routing services and their current driving profile where they explain behavior or configuration.

Route creation uses addresses, coordinates and map points. The route-description interpreter has been removed; keep this direct editing flow simple.

## Contracts to preserve

- `Coord` is `[latitude, longitude]`. OSRM URLs and GeoJSON use longitude first; convert at the adapter boundary. Preserve every full-resolution track point and separate GPX track segments. Escape user-provided XML text.
- Server URLs live in two places by design: OSRM, Valhalla and Nominatim are part of `State` (links when non-default, JSON editor, saved routes, backups); Photon, Open-Meteo and the IP-region service are device preferences in localStorage (`photon-url`, `weather-server`, `region-url`) and never enter links, saved routes or backups; the same applies to the `average-speed`, `distance-units`, `temperature-units`, `route-coloring`, `route-arrows`, `weather-markers`, `auto-departure` and `navigation-notice` preferences. Moving a server between the two changes the state/link format and needs compatibility handling.
- Servers carried by a link are never used without an explicit choice: a link with non-default routing/search servers opens with the defaults and a notice offers Use link servers. Settings, the JSON editor, saved routes and backups remain explicit user flows.
- Router responses are untrusted: the OSRM and Valhalla adapters build routes through `validRoute` (also used for backups) and reject malformed geometry or values, letting OSRM failures fall back to Valhalla.
- Route steps may carry optional maneuver details: `kind` in OSRM's maneuver-type vocabulary, `modifier` from `MODIFIERS`, a roundabout `exit` (integer 1–20) and the maneuver location `at` as `[lat, lon]`. Both adapters map to this shared vocabulary (Valhalla through `VALHALLA_TYPES`) and omit values outside it; `validRoute` rejects malformed ones in saved routes and backups. The fields stay optional so older saved routes and `route-gpx-library` v1 backups remain valid and reopen without rerouting.
- Imported GPX, TCX and FIT geometry remains exact until a point edit causes rerouting. FIT and TCX import reads only geometry, names, course points and recorded elevation, locally; sensor data is ignored and never stored, and export stays GPX only. A share link stores controls/options, not that geometry, and recalculates when opened. Do not imply that links preserve imported tracks.
- `State` uses version 1. Links are written as `#v2=` (base64url raw DEFLATE via fflate of a positional array, coordinates rounded to 6 decimals, default servers omitted) and `#v1=` links (base64url JSON) remain readable. Keep existing links and the advanced JSON editor compatible; validate links, editor JSON and backups with `validateState` rather than trusting parsed JSON. Legacy speed and `units` values in links, editor JSON and backups are ignored without discarding valid route points.
- Editing a route invalidates the current result and disables stale downloads. Preserve revision checks and discard superseded work so late routing/search responses cannot overwrite newer input or another point's results.
- Language, units and GPX coordinates are independent. Units are device preferences chosen in Settings (`src/unit-preferences.ts`): distance (km/mi: distances, speeds, wind, altitude) and temperature (°C/°F, with weather precipitation in mm/in), each Automatic by default, inferred locally from the device's time zone and, when it names no place (UTC, `Etc/*`), the browser's language region, never from a request (a language region often names only a variety of the language, such as `en-GB` in Australia). Links, saved routes and backups do not carry units (the `#v2=` units slot is kept as 0). Weather requests and risk thresholds stay metric; unit changes only reformat and must not reroute, refetch or alter geometry. Time, arrival, weather passage times and daylight all use the traveler's average speed, never the router duration. That speed is a device preference in localStorage (`average-speed`, default 60 km/h) changed only by the user (slider, or the unit switch converting it); links, saved routes and backups do not carry it, and legacy values in them are ignored (the `#v2=` speed slot is kept as 0).
- Undo retains up to 50 snapshots in memory, each holding a reference to the route shown for it, so undo restores that exact geometry without rerouting; there is no separate route cache for undo. Preserve point move/removal/reordering behavior and the keyboard shortcut's exclusion of text inputs.
- Routes are saved only by an explicit named save. IndexedDB entries use normalized names for updates; reopening/downloading stored geometry must not request a new route. The one request allowed for a stored route is the step-only refresh when the Itinerary of a route saved before maneuver details existed is opened (`src/directions.ts`): its steps replace the old ones only when the fresh route follows the saved geometry (`sameRoad`), and `updateSavedSteps` stores only the steps, keeping geometry, name and dates; when the road changed, `markDirectionsChecked` records it in the entry (optional `directionsChecked`) so it is not asked again. Storage failure must leave ordinary GPX download usable.
- Backups use the `route-gpx-library` version 1 format. Validate the complete import before writing and keep existing entries with matching names. Do not silently discard saved data or change persistence formats without handling compatibility.
- “Prefer main roads” is a heuristic review aid, not a guarantee. Keep provider road references factual; do not invent classifications.

## Network behavior and privacy

Use every external service within its published terms: rate limits, no heavy or bulk use, a valid User-Agent and Referer (the browser's own) and the required attribution. `docs/SERVICES.md` records each policy with the date it was checked; recheck it when changing how a service is used, and state the worst-case request rate of any new automatic request pattern against those terms. Use the adapters in `src/services.ts` for routing/search. Imported tracks get turn directions only when the Itinerary is opened, through OSRM map matching (`osrmMatch`): points evenly spaced within each leg (restarting at every route point, spacing ladder from 300 m, about 40 requests), requests of at most 10 points (the public server's limit) that never cross a route point, on the routing queue, without retries, with a page-memory cache of 400 requests for 15 minutes so an edit re-requests only the changed legs; the imported geometry never changes. OSRM is primary, with a delayed Valhalla fallback. Preserve serialized routing starts at least 1.5 seconds apart, the 900 ms route-change debounce, and suppression of stale queued calculations. Do not introduce retry loops. Without a connection (`navigator.onLine` false), Calculate route keeps the route on screen and sends nothing, and a calculation that fails offline says the route will be calculated when the connection returns, then makes one new attempt on the browser's `online` event if nothing changed meanwhile; this single attempt is not a retry loop. The one exception is the Open-Meteo usage limit (the shared per-page budget of 599 coordinates a minute, 4,999 an hour, 9,999 a day and 299,999 in 31 days, or HTTP 429): weather and elevation show a live countdown (`countdown`, "Try again in 30s.") with no retry button, then retry once on their own; refused again, they count down once more and only then show the button. Use Retry-After when the response exposes it, otherwise wait 60 s.

Nominatim searches are explicitly triggered with Enter, not autocomplete. Photon suggests places while typing; do not restore the removed search buttons. Preserve the 500 ms UI debounce, 1.1-second search spacing, in-memory query cache and cross-tab coordination through Web Locks/timestamp storage where available. The timestamp is not a location store. Client-side limits do not enforce aggregate traffic limits across devices.

Keep fetch credentials omitted and service URL validation intact. Retain visible OpenStreetMap attribution. Do not add tile prefetching, bulk downloads or offline tile caching. Locations belong only in the existing explicit route/link/storage flows; canonical URLs, social metadata and sitemap entries must never contain user route state.

Weather is optional: no departure means no Open-Meteo request. A valid departure triggers a debounced request automatically. Without a chosen departure, the automatic departure (`src/departure.ts`) is the next local :00/:30 slot (`nextDepartureSlot`): it applies once the route is ready (so weather is requested without a click), moves forward at each slot while the page is visible (not while the field has focus, catching up when a hidden tab returns) and is used by weather, daylight, arrival and playback through `departureOf`. It lives in page memory only and never enters links, saved routes, backups or the JSON editor; only a departure the user chose is `state.departure`. The Automatic departure checkbox below the field shows the mode: any user edit fixes the departure and unchecks it, clearing turns it off until reload, checking it returns to automatic, and unchecking it by hand stores the `auto-departure` device preference as off. Without a departure, Weather asks for one. Support the last 90 UTC calendar days and the 16-day forecast horizon. Sample about every 20 km (or one hour for slow travel), including controls, spacing samples evenly within each leg between route points so none lands beside a control, with at most 20 points; points left free go to sharp bends (`routeBends`, `BEND_THRESHOLDS` in `src/weather.ts`, 60° or more), largest first and away from other samples, never displacing distance samples; consecutive samples with equivalent conditions (`groupWeather`, `MERGE_THRESHOLDS` in `src/weather-risk.ts`) share one card and one marker with ranges, while start, stops and destination always keep their own; with more than 20 controls, keep start and destination and choose the controls closest to an even spread (named before automatic stops) and say how many were sampled, never fail or ask the user to remove points. Use a worst-case ±1 hour window rounded outward. Keep weather and sampling coordinates in page memory only; only departure belongs in existing explicit route/link/backup flows. Wind direction is meteorological (from), compared with the local full-resolution track bearing; use the outgoing edge at bends and incoming edge at the destination, never GPX segment gaps. Show head/tail/crosswind at the nearest hour in selected units; do not imply apparent wind or vehicle resistance. Do not restore the removed planned-stop field or forecast button. Slower speeds may require additional points; otherwise recalculate times locally.

Keep route caching bounded to 20 results for 15 minutes; Calculate route bypasses it. Weather caches are per rounded location and interval, at most 200 locations/100,000 hourly entries for ten minutes. Cache hits must not extend freshness. All these caches stay in page memory. Map wind arrows show the direction wind blows toward; colors indicate head/tail/crosswind relative to the route; calm or unknown is neutral. Mean-wind strength remains separate from gust risk thresholds.

Elevation is requested only when the user opens Elevation or chooses the Grade route coloring (`gradeRanges` in `src/elevation.ts`, five classes at ±3 % and ±8 % over `GRADE_WINDOW`), or for one point when the user chooses Elevation here in the map point menu (one coordinate per explicit choice, same queue, budget and cache; never on hover or move; also available while editing is locked); a recalculated route waits 2 s to settle while either is on: at most about 300 sampled route points, evenly spaced within each leg from a fixed spacing ladder so an edit re-requests only the changed legs, to the configured Open-Meteo server (`/v1/elevation`), in serialized chunks of 100, no retries, page-memory cache of 5,000 locations for ten minutes; recorded elevation from imported GPX `<ele>`, TCX `AltitudeMeters` or FIT altitude is used locally without requests and is not stored. Road attributes (surface) are requested only when the user opens Surface or chooses the Surface route coloring; a recalculated route waits 2 s to settle while either is on: the route geometry in pieces of at most 190 km (the public server's 200 km trace limit), grouping whole legs between route points in order (one request per 190 km however many stops) and never across GPX segment gaps, at most 10 pieces, by POST to the configured Valhalla server's `/trace_attributes`, serialized on the routing queue, no retries (a failed piece is unknown, HTTP 429 stops the rest), page-memory cache of 100 pieces for 15 minutes; responses go through `parseTraceAttributes` as untrusted data. Valhalla assumes a surface from the road class where OSM has none (ordinary roads become paved, only tracks dirt) and does not say so; keep that limitation, and the direction of its error, visible and never invent classifications. Daylight is calculated locally from the route and the same passage times as weather (the device average speed, no stops): no requests and no stored data. Route coloring and route marks are visual only and never change the route, links or GPX. Weather belongs to the route: it is shown only for the departure-based samples along it. Do not add map-wide weather overlays such as rain radar, cloud or forecast layers (rain radar was removed). Keep weather attribution in the existing map credits dialog. The only service worker allowed is the same-origin app shell described under Guided navigation; there is no install prompt or installation flow beyond Add to home screen, which only shows the browser's own steps (`src/home-screen.ts`).

## Guided navigation (#31)

Guided navigation follows these rules, agreed in #30; the issues that implement them update the README, help, privacy disclosures and `docs/SERVICES.md` when they ship. The first part has shipped: Navigate in the phone action bar opens a full-screen view (`src/navigation-ui.ts`) that follows the route with the next maneuver, the one after it, the remaining distance and time and the arrival, on a heading-up map. The map follows the direction of travel while moving and the device compass when stopped (`isMoving` hysteresis in `src/navigation.ts`), since mounts and car metal make the compass unreliable in motion; orientation readings stay on the device like positions, and the magnetic heading is turned to true north with the local WMM2025 declination (`src/declination.ts`, public-domain coefficients checked against NOAA's test values; replace them with WMM2030 when it is published). The traveler can zoom (pinch and MapLibre's double-tap-and-drag zoom, both around the map center, and a double tap handled in `src/navigation-ui.ts` that also zooms around the center, so following keeps the traveler in place), pan with one finger and turn the map with two (past MapLibre's rotation threshold, so a pinch only zooms); following keeps a chosen zoom, while a pan or turn leaves a free view that the compass no longer turns. Any view other than following heading-up at the default zoom shows Re-center at the bottom left; the compass button, shown only on a turned map, puts north up (and following then stays north-up until Re-center). The browser's callout, loupe and selection are blocked on this screen (touches on the map cancelled, selection off on the whole page while navigating), since iOS ignores `-webkit-touch-callout` on the map itself. The navigation map (#140) is MapLibre GL JS with OpenFreeMap vector tiles (`liberty` style adjusted in `src/navigation-style.ts`: local `name` labels, streets and roads twice as wide with names sized to stay inside them), loaded lazily on Start navigation so the planner keeps Leaflet with raster tiles; it turns with its native bearing, so labels stay upright, and its credits use the planner's modal (`creditsDialog` in `src/map-credits.ts`). Without WebGL the screen shows a notice and the directions only. Return to route, rerouting and voice are still to come.

- Continuous location: `watchPosition` starts only after an explicit Start navigation, shows a visible indicator while active and stops on End, when the page is hidden and when navigation ends. Positions stay in page memory only: they never enter links, saved routes, backups, the JSON editor, storage or requests, except the reroute request below.
- Return to route is local first. Built on `src/track-position.ts` (progress, off-route distance, pass choice by progress), it shows the direction and distance to a rejoin point ahead on the track, never behind the current progress, labeled as a straight-line hint that does not know the roads. It needs no request and works offline. Off-route detection is accuracy-aware with hysteresis and tolerates intentional deviations, since the traveler may use any mode while routes use the driving profile.
- Rerouting is online only and within the routing servers' terms (the public OSRM and FOSSGIS servers allow at most one request per second and no heavy use). It is automatic only when the device is online and the traveler stays off route beyond the accuracy-aware threshold for a sustained time, at most once every 60 seconds, through the existing serialized routing queue (starts at least 1.5 s apart) and without retries: a failure keeps the local hint until the next interval. An explicit Reroute button uses the same queue and limits. The request carries the current position rounded like Use my location (about 100 m), the only position ever sent. #31 fixes the exact threshold, duration and per-session cap with tests, within these bounds.
- Without tiles or the map style, the route line, maneuvers and position still draw over a neutral background with a notice; navigation never depends on tiles. The tile rules above stay: no prefetching, no bulk downloads and no offline tile caching, which the OpenStreetMap tile policy forbids.
- Screen and voice: request a Screen Wake Lock while navigating and release it on stop, and say that browsers stop tracking with the screen off or the tab hidden. The start notice says it without naming a browser; the help and README add that iOS Safari is the strictest. Voice announcements use the local `speechSynthesis` only, off by default; no remote speech service.
- Safety: a large-text navigation view with few controls. A notice when navigation starts gives only safe-use recommendations (avoid handling the phone while moving, use a mount in view, check the route before leaving; keep the tab open and the screen on), with a Don't show this notice again checkbox stored as the `navigation-notice` device preference and turned back on in Settings; it does not block use, because the traveler needs the screen to find the way and a passenger may be the one using it.
- Service worker (`src/sw.ts`, #126): it caches the same-origin build files of one build only (the app, help and What's new, their hashed assets, icons, manifest and notices, listed by `precacheList` and versioned by a hash of their contents in `vite.config.ts`), so a saved route opens and can be followed without network. Pages are network-first with a 4 s fallback to the cached page, and a fresh page is never stored, so a page and its assets always come from the same build; registration uses `updateViaCache: 'none'` and a new build replaces the old cache on activation. It never intercepts or caches cross-origin requests (tiles, routing, search, weather, elevation, road attributes, IP region); route data stays in the existing IndexedDB library. A new deploy must activate predictably, never leaving an outdated app in use, and the manifest keeps `display: browser` with no install prompt (Add to home screen only explains the browser's steps).

## Interface, text and assets

Do not add project UI screenshots to the repository or the README. Use the project logo for presentation; existing icon and social metadata brand assets are allowed. Keep local acceptance captures in an ignored `*.local/` directory.

Never use emoji characters as authored interface icons or decoration. Use the shared inline SVG system in `src/icons.ts`, with a 24-unit viewBox, 2-unit strokes, rounded ends and `currentColor`. Apply it to weather cards/markers, alerts and controls. Decorative SVGs must be hidden from assistive technology; retain meaningful text and accessible names. Preserve user-provided route names and required copyright attribution as text.

Check every interface change at its extremes before it is called done or offered for approval: the narrowest supported phone width (320 px) through 360, 390 and 430 px phones to wide desktop, both languages, the longest realistic values (time ranges across midnight, long place and route names, imperial units, alerts) and fonts wider than the local one (CI renders with DejaVu Sans). Text that wraps where it should stay on one line, overflows, overlaps or is clipped at any of them is a failure: adjust the layout until it passes, then keep the case in a browser test that measures it.

Use at least 16px text in editable touch controls to avoid iOS focus zoom. On phones only the maps zoom (#131): `touch-action: manipulation` on every page removes double-tap page zoom, and the planner page (`body.planner`) also blocks pinch zoom of the page, since everything fits from 320 px; Help and What's new keep pinch zoom. Never lock the viewport (`user-scalable=no` or `maximum-scale`), so browser text size and forced-zoom accessibility settings keep working. Keep the compact mobile layout, keyboard-accessible controls and high-contrast light theme, including when the OS prefers dark mode. Use the separate help page for detailed usage instructions; it is for site users only, so keep development, build, test and deployment information in the README and repository documentation.

Keep English source keys and Portuguese translations together in `src/i18n.ts`; check both language directions. Keep redistributed dependency notices in `public/THIRD_PARTY_NOTICES.txt` and link them from the README and help. Adding or changing an external service requires updating the README, help, privacy disclosures and required source/license credits.

When changing English UI text, update its exact key or dynamic pattern in `src/i18n.ts` and verify switching back and forth. Translation caches original DOM text and selected attributes; do not replace this mechanism casually. Update the README and help instructions when user-visible behavior changes, and add the change to `CHANGELOG.md` and both languages of `changelog.html` (What's new) under Unreleased in the matching Keep a Changelog section; internal changes get no entry.

`main` is protected by the `Protect main` repository ruleset: pull requests are required, merges are squash-only with linear history, the `Lint, test and build` CI check must pass on a branch that is up to date with `main`, and review conversations must be resolved. Force-pushes and deletion are blocked, and the ruleset has no bypass actors. Never push directly to `main` or try to work around these protections. ## Hosting and publication

Pages serves the custom-domain root with an approved certificate and enforced HTTPS. Changing the Pages domain, DNS or HTTPS settings is a separate authorized infrastructure task. Preserve Vite's `/` base for the custom domain and the app, help and What's new (`changelog.html`) build entries. A hosting-path change also requires reviewing manifest `id`/`start_url`/`scope`, canonical/social URLs, sitemap and docs; root-relative paths can break on a Pages project site.

Three workflows handle checks, publication and monitoring. `.github/workflows/ci.yml` (CI) runs the static checks, unit tests and build in one job and the browser suite in 4 shards, merges their reports and reports the result through the `Lint, test and build` gate job for pull requests, main pushes and manual dispatch with only `contents: read`, in the non-cancelling `ci-<ref>` concurrency group. `.github/workflows/deploy.yml` (Deploy) runs through `workflow_run` only after a CI run triggered by a push to `main` succeeds; it rebuilds that run's exact `head_sha` and publishes it to Pages. Preserve Deploy's `pages: write` and `id-token: write`, its non-cancelling `pages` concurrency group and its current-main guard, which skips publication when the commit is no longer the current `main` so an older commit cannot publish over a newer one. `.github/workflows/lighthouse.yml` (Lighthouse) runs `npm run lighthouse` against the live site with three runs per page on Dependabot's schedule (Monday 00:00 UTC) and on manual dispatch, with only `contents: read` in the non-cancelling `lighthouse` concurrency group; it posts the score table to the run summary and the reports as an artifact, is not a required check and never builds or publishes. A failed audit is a regression to investigate in its own task, not a reason to rerun it. Keep Pages permissions out of CI and do not add a manual trigger to Deploy. Never rerun old workflow executions to publish; watch only the runs belonging to the authorized new commit.

When publication is part of the task, deliver the change through an authorized pull request as described above; the push to `main` comes from its squash merge. Then follow the CI run for the merge commit on `main` and the Deploy run it triggers with `gh run watch <id> --exit-status`, and distinguish successful checks from successful deployment. Confirm the requested behavior on the live site; do not infer it from a green build alone.
